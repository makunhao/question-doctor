# 黄金测试集（benchmark）

> 用途：用**人工标注的期望值**，量化引擎判定的准确率，而不是只测"代码有没有按我设想的方式跑"。
>
> ```bash
> python scripts/run_benchmark.py          # 跑基准（CI 用；退出码 0 = 无新回归）
> python scripts/run_benchmark.py --all    # 连已知缺口一起列出来
> python scripts/run_benchmark.py --json   # 给别的程序消费
> ```

---

## ⚠️ 先说清楚这个测试**不能**证明什么

**标注是我本人做的。**

这意味着：**它测的是"引擎是否符合我的判断"，而不是"引擎的判断是否正确"。**
两者在"规则实现有没有跑偏"上是等价的（这正是我要测的），
但在"这套判据本身合不合理"上**完全不等价**——我可能把一条错误的期望标得很自信。

具体地：这里的"误报率 4.17%"不能读成"客观误报率 4.17%"，
只能读成"**在我认定的标准下**，引擎有 4.17% 的判定与我的预期不符"。

**要真正解决这一点，需要非本人标注、或来自真实使用场景的独立样本集。**
当前没有。**这一栏我不填，也不假装填过。**

> 加这条说明的起因很直接：一份同类提交拿到了 92 分，被扣的第一条就是
> 「评审器对自身提交打 100 分……仍缺乏独立第三方样本的交叉验证」。
> 同一个坑，我不打算再踩一次。

## 口径定义（方向别搞反）

| 术语 | 定义 | 伤害 |
|---|---|---|
| **误报** | 引擎判「缺失」，但标注是「存在」 | **冤枉用户**。会诱导他把已经写好的部分再改一遍——甚至为了"过检查"而堆内容 |
| **漏报** | 引擎判「存在」，但标注是「缺失」 | **放过问题**。用户以为万事大吉，发出去仍然没人回 |

两者伤害不对称：**误报会催生"度量劫持目标"的行为**（这正是本项目的第 1 条继承教训），
所以它被单独统计，且在基线对比里权重最高。

## 「已知缺口」是怎么处理的

黄金集里有 8 处判定与我的标注不符，**它们是关键词方案的固有局限，不是漏改的 bug**：

| 根因 | 缺位数 | 例子 |
|---|---|---|
| **词法无法区分同构表达** | 2 | 「20 个页面」（规模）vs「18 篇输出 0 字符」（问题度量）；「我试过了」vs「我试过 A，结果 B」 |
| **规则表只覆盖中文** | 6 | 整条英文用例的 5 处误报 + 因此导致的通过判定不一致 |

处理方式：登记进 `benchmark/known_gaps.json`，**每条都写明"为什么修不掉"和"代价是什么"**。
跑测试时它们被识别为「已知」，**CI 只对「新出现的错误」报红**。

> 为什么不让 CI 直接报红：一跑就红的灯，人会习惯性忽略——那这个测试等于没有。
> **灯的语义必须是"有东西变了"，而不是"这里一直有问题"。**

> 为什么每条都要写"为什么修不掉"：只写「先忽略」等于把问题藏起来。
> 而这些理由本身是有价值的结论——它们恰好划出了**确定性规则的能力边界**，
> 也就是语义层（LLM）该接手的地方。

## 基线

`baseline.json` 记录当前水平。CI 会对比：

- 误报数 / 漏报数 / 负面错误数 **变大** → 报红
- 类型准确率 / 通过一致率 / 媒介一致率 **下降** → 报红
- 只是"和之前一样"→ 绿灯

所以改规则的流程是：改 → 跑 → **如果变好，更新基线并记进 CHANGELOG**；
如果变差，要么修回来，要么在 `known_gaps.json` 里给出理由。

## 加一条用例

```jsonc
{
  "id": "G19",
  "title": "一句话说清这条在测什么",
  "input": "……被诊断的正文……",
  "expect_type": "question",              // 或 null（类型本身有歧义，不参与统计）
  "expect_present": ["上下文", "具体卡点"], // 该类型下**应当被判为存在**的要素
  "expect_partial": ["已尝试"],            // 可选：应当只给一半分的
  "expect_negative": ["甩手式求助"],        // 可选
  "expect_pass": false,
  "expect_ready_to_send": false,           // 可选："能不能直接发"（含媒介适配）
  "expect_medium_level": "bad",            // 可选
  "rationale": "为什么这样标注——这一栏比标签本身更重要"
}
```

**两条纪律**：

1. **先标注、后运行。** 期望值只能依据文本本身判断，不许看了引擎输出再改标签。
   否则测的就是"引擎和它自己一致"，毫无意义。
2. **改了 `input` 就必须重标。** 正文一变，原来的标注就不再对应这段文字了——
   本次就发生过一次：G13 的正文被我加长之后，旧标注立刻失效，跑出来一堆假问题。
